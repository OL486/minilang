# 性能基线：tree-walking vs 字节码 VM

**这一篇的产出是一组数字，不是代码。** 没有基线，「为什么要引入字节码」就只是一个说法。

所有数字来自同一次会话、同一台机器（Windows / amd64 / Go 1.26.1 / RTX 4060 笔记本），
测量方法在文末，可以原样复现。

---

## 1. S5 基线（tree-walking，VM 还不存在时的唯一证据）

被测程序（`cmd/minilang/main.go` 里的 `benchSource`）：

```minilang
fn fib(n) {
  if (n < 2) { return n; }
  return fib(n-1) + fib(n-2);
}
let benchResult = fib(30);
```

用 `let` 接结果而不是 `print`，避免 I/O 时间混进测量区间。
`fib(30)` 一共 2,692,537 次调用（`fib(0)` 到 `fib(30)` 的调用次数），
足以让常数项噪声被摊薄。

| 会话 | 第 1 次 | 第 2 次 | 第 3 次 | 中位数 |
|---|---|---|---|---|
| 1 | 1377.0 ms | 1361.4 ms | 1773.5 ms | **1377.0 ms** |
| 2 | 1402.5 ms | 1400.8 ms | 1740.5 ms | **1402.5 ms** |
| 3 | 1354.8 ms | 1425.5 ms | 1761.1 ms | **1425.5 ms** |

**S5 基线：1.40 s**（三次会话中位数的中位数）。

注意每次会话的**第三次**都明显更慢（1.74–1.77 s，比其他两次高约 25%）。
这不是抖动，是 Go 自己的 GC 在起作用：tree 引擎每层作用域都 `make(map[string]any)`，
分配量很大，前两次跑完之后堆已经膨胀，第三次触发了更重的回收。
这条观察本身也是基线的一部分 —— **tree-walking 的成本不只在线性时间上，还在分配量上**。

## 3. 对比表（S10 产出）

| 指标 | tree-walking（S5） | 字节码 VM（S10） | 变化 |
|---|---|---|---|
| `fib(30)` 耗时（中位数） | **1402 ms** | **161 ms** | **8.7× 加速**（复测区间 8.4–8.7） |
| 单次运行波动 | ±10%（第三次 +25%） | ±3% | 显著更稳 |
| 每层调用分配 | 1 个 `map` + N 个闭包 | 0 次分配 | — |
| Go 堆（运行前后） | 435 KiB → 403 KiB | 1.45 MiB → 1.38 MiB | VM 常驻更高 |
| 对象堆（自管） | 无（用 Go 的 GC） | 几百个对象，~0.8 MiB | — |
| Go 源码行数 | — | 3970 行（非空非注释 3426 行） | 全项目 |
| `go build` / `go vet` | 通过 | 通过 | — |

关于内存那一行的两点说明，避免误读：

- **VM 的 1.38 MiB 里大约 1 MiB 是预分配的 32768 槽操作数栈**（每个 `Value` 32 字节）。
  这是刻意的：栈永不 realloc，因为 `ObjUpvalue.Location` 直接指向栈内地址，
  搬家会让所有 open upvalue 失效。换来的是运行期**零分配**。
- tree 引擎的 Go 堆看起来更小，是因为它的分配全交给 Go 的 GC 处理，
  而 `readHeap` 读的是回收后的 `HeapAlloc`。它的**分配总量**远大于 VM
  —— 这也解释了为什么它的第三次运行会慢 25%。

## 4. GC 的独立验收（S9）

`examples/05-gc-stress.ml`：20 万次闭包创建 + 3000 次字符串拼接 + 5 万次块作用域临时对象。

```bash
minilang run examples/05-gc-stress.ml --stats
minilang run examples/05-gc-stress.ml --stats --gc-off
```

| 指标 | GC 开启 | GC 关闭 |
|---|---|---|
| 累计创建对象 | 403,015 | 403,015 |
| 运行结束存活对象 | **288** | **403,015** |
| 自管对象堆 | **785,347 B (0.75 MiB)** | **23,822,225 B (22.7 MiB)** |
| GC 次数 | 22 | 0 |
| 结果正确性 | 正确 | 正确（但内存不收敛） |

22 次 GC 回收掉 40 万个对象，存活数从 40 万降到 288 —— 差 1400 倍。
这张表是「标记-清除真的在工作」的唯一证据；`--gc-off` 那一列是它的对照组。

如果只看「没崩」，两个配置都算通过。所以验收标准必须是**存活对象数**，不是「能不能跑完」。

## 5. 字节码到底换来了什么

### 换来的

1. **变量访问从「查名字」变成「数组下标」**。
   tree：`env.Lookup("n")` → 沿 `map` 链逐层 `map[string]any` 查找 + 字符串哈希。
   VM：`stack[slotBase+1]` → 一次加法 + 一次下标。
   这是 8.7 倍里最主要的一项。

2. **值不再装箱**。
   tree 的每个值都是 `any`（interface）：`float64` 装进 interface 会堆分配，
   每次算术都要做动态类型断言。
   VM 的 `Value` 是 24–32 字节的定长结构体，算术是 `switch` + 直接取 `num` 字段。
   这一项和上一项混在一起，我没有做分离实验（见 `docs/02-pitfalls.md` 末尾）。

3. **每个 AST 节点只遍历一次，而不是每次执行都遍历一次**。
   tree 引擎执行 `fib` 函数体时，每一层递归都要重新 `switch` 遍历 AST 节点。
   VM 把 AST 压平成字节码，执行期不再有任何指针追逐（`chunk.Code` 是连续数组）。

4. **稳定性**。tree 的耗时波动 ±10%，VM 是 ±3%。原因在分配量：
   分配少 → GC 压力小 → 延迟可预测。对交互式程序，这比峰值吞吐更重要。

### 没换来的

1. **字符串密集场景的优势**。每次拼接都要查驻留表 + 可能分配 + 可能触发 GC。
   `fib` 是纯数值，所以数字好看；`examples/05` 里那个 3000 次拼接的循环，
   两个引擎的差距就小得多。

2. **更小的内存**。VM 常驻内存更高（预分配的栈 + 自己的对象堆）。
   字节码换的是「运行期零分配」，不是「总内存更少」。

3. **更简单的实现**。编译器比 tree 引擎难写得多：槽位分配、跳转回填、
   upvalue 描述表、GC 根集合，每一项都能单独写出一个 bug。
   tree 引擎 700 行，字节码这条线（compiler + engine）2000 行左右。

## 6. 复现方法

```bash
go build -o minilang.exe ./cmd/minilang

# S5 基线（tree-walking）
./minilang.exe bench --engine=tree

# S10（字节码 VM）
./minilang.exe bench

# GC 验收
./minilang.exe run examples/05-gc-stress.ml --stats
./minilang.exe run examples/05-gc-stress.ml --stats --gc-off
```

`bench` 的测量口径：

- 词法/语法/编译在计时区间**之外**（只测执行），
  所以 tree 与 VM 的差值就是「执行模型」的差值，不含前端；
- 同一个解释器/VM 实例连跑 3 次，取中位数；
- 每次运行前 `runtime.GC()` 再读 `HeapAlloc`，所以内存数字是「回收后常驻量」，
  不是峰值；
- 行数统计由 `bench` 自己做（`countLOC`），不依赖外部脚本，任何机器上跑出来的口径一致。

**换机器跑出来的绝对值会不一样，但 8–9 倍这个量级应该稳定。**
如果你的结果差距明显小于 5 倍，先检查 `--engine` 是不是真的切过去了
（`bench` 第一行会打印当前引擎）。
